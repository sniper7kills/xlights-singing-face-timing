xLights Singing Face Timing Generator

xLights Singing Face Timing Generator

Overview

The app is a web application for people who build light shows with xLights. The person loads an audio file of a song. The app finds each sung word and the time of each word. The app then converts each word into the mouth shapes that xLights uses to animate a singing face.

The app writes the result as an .xtiming file. xLights imports that file as a timing track that has three layers: phrases, words and phonemes. The Faces effect in xLights reads the phoneme layer and moves the mouth of a face model.

The same work in xLights is manual today. The person types the lyrics, then drags each phrase, each word and each phoneme into position by ear. A three-minute song can take several hours. The app does the first pass in minutes and gives the person an editor to correct the result. Audio leaves the browser only when the person selects a remote endpoint, and the app shows the host first. The app has no server that receives audio.

The user's request, verbatim:

I want to create a web-based project that will help me synchronize recordings word-by-word into an xlights compatable .xtiming to anamate singing faces. Ideally I can upload the audio file to the website and then have the xtimings file generate. Extra points if we can help generate the files however it would be easiest to import for multile faces/sections of the song. Include a nice GUI. Analyze xlights; and all relivant settings.

Goals

  1. A person gets a first-pass .xtiming file from an audio file in less than 10

minutes for a 4-minute song on a desktop computer with WebGPU.

  1. xLights imports every exported file without an error message, with three layers

for each timing track.

  1. The Faces effect in xLights animates a face model from an exported timing track

with no manual edit in xLights.

  1. A person corrects a wrong word time in the editor in one drag action.
  2. A person exports one file that holds one timing track for each voice.
  3. Audio leaves the browser only when the person selects a remote endpoint, and the

app shows the host first.

Non-goals

  • The app does not edit xLights sequences (.xsq), layouts or face definitions.
  • The app does not place Faces effects on models. The person does that in xLights.
  • The app does not separate the vocals on a server, and it does not separate

stems other than the vocals.

  • The app does not have accounts, a server database or shared songs.
  • The app does not read or write Papagayo .pgo files in v1.
  • The app does not support phone-size screens in v1. The minimum width is 1024 px.
  • The app does not include a paid speech service. A remote endpoint belongs to the

person.

  • The app does not support dictionaries for languages other than English in v1.

Users & personas

The sequencer. A hobbyist or a professional who builds xLights shows. This person knows xLights timing tracks and face models. This person does not know phonetics or speech models. This is the only persona. Every person has every permission, because all data stays in that person's browser.

The sequencer needs to:

  • load a song and get words with times without a setup step,
  • see and hear where each word starts and ends,
  • correct errors fast with the mouse and the keyboard,
  • give each singer a separate timing track,
  • get a file that xLights imports on the first attempt.

The app is a static single-page application. It has no backend. Each component:

  • React UI. React 19.3 with TypeScript 7.0, built with Vite 8.3. React with Vite

is the user's choice. Next.js adds a server that the app does not need.

  • Song store. Zustand 5.1 holds the open song in memory. A plain store keeps the

undo history simple. Redux adds ceremony that one screen does not need.

  • Waveform. wavesurfer.js 8.1.1 (BSD-3-Clause) draws the waveform and plays the

audio. The app draws the three layers with its own React components above the waveform, on the same time scale. The Regions plugin of wavesurfer.js puts all regions on the waveform itself, which does not fit three stacked layers. Verified against: https://wavesurfer.xyz/docs/ (retrieved 2026-11-24) and npm view wavesurfer.js version (8.1.1).

  • Transcribe worker. A Web Worker runs @huggingface/transformers 4.3.2

(Apache-2.0) with a Whisper speech model. The worker keeps the UI responsive. The library accepts device: 'webgpu' and returns word times when the call passes return_timestamps: 'word'. Browser Whisper is the user's choice and the default. The person can select a remote endpoint that is compatible with the OpenAI transcription API, for example a self-hosted server (issue #101, docs/adr/0007-remote-whisper-endpoint.md). Verified against: https://huggingface.co/docs/transformers.js/api/pipelines and https://huggingface.co/docs/transformers.js/en/guides/webgpu (retrieved 2026-11-24), npm view @huggingface/transformers version (4.3.2).

  • Dictionary module. Pure TypeScript. It looks up CMU symbols and maps each

symbol to a phoneme label with the table that xLights uses. Verified against: resources/dictionaries/phoneme_mapping in https://github.com/xLightsSequencer/xLights (commit 99a289bf).

  • xtiming writer. Pure TypeScript. It produces the XML text that

TimingElement::GetExport() and RowHeading.cpp produce in xLights. Verified against: src-core/render/Element.cpp, src-ui-wx/sequencer/RowHeading.cpp and src-core/render/SequenceFile.cpp in https://github.com/xLightsSequencer/xLights (commit 99a289bf).

  • IndexedDB. The browser database stores songs, audio files and the custom

dictionary. The app uses the native IndexedDB API behind one small module.

  • Hosting. A private Amazon S3 bucket holds the built files. An Amazon

CloudFront distribution serves them through an origin access control. A CloudFront response headers policy sets the security headers. A GitHub Actions workflow deploys each commit on main. S3 with CloudFront is the user's choice over AWS Amplify Hosting: it gives more control and a lower cost at scale. One CloudFormation template, infra/hosting.yml, declares all hosting resources. Verified against: https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-cloudfront-originaccesscontrol.md, https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-cloudfront-responseheaderspolicy-securityheadersconfig.md, https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-idp_oidc.html (retrieved 2026-11-24), and aws s3 sync help, aws cloudfront create-invalidation help (aws-cli/2.37.9).

What xLights requires (analysis of the xLights source)

These facts drive the design. Each one comes from the xLights source at commit 99a289bf.

  • An .xtiming file is XML. The root is one <timing> element, or one <timings>

element that holds several <timing> elements.

  • A <timing> element has the attributes name, subType and SourceVersion.

The import code reads name and subType only.

  • Each <EffectLayer> child is one layer. Each <Effect> child of a layer is one

mark with the attributes label, starttime and endtime. Times are whole milliseconds.

  • The import code moves each time down to a multiple of the sequence frame size

(s -= s % GetFrameMS()). A mark shorter than one frame can become zero length.

  • The import code renames a timing track when the name exists in the sequence.
  • The Faces effect reads layer index 2, the third layer, for the mouth. It shows

rest when the timing track has fewer than three layers.

  • The Faces effect shows rest at any time that has no phoneme. A gap between

phonemes is a closed mouth.

  • The phoneme labels are AI, E, etc, FV, L, MBP, O, rest, U, WQ.

Labels are case-sensitive: etc and rest are lower case.

  • The eyes of a face blink in Auto mode while the phoneme is rest.
  • xLights exports a Papagayo file only from a timing track with exactly 3 layers.

  • Song. id is a UUID. name defaults to the audio file name without the

extension. durationMs comes from the decoded audio. frameMs is 25 or 50, and the default is 50. A song lives until the person deletes it.

  • Audio file. The original bytes of the file, stored once for each song.
  • Voice. name is unique in a song, 1 to 60 characters. order sets the row

order and the export order. color is one of 8 preset colours. A new song has one voice named "Lead Vocals".

  • Section. name is 1 to 40 characters. startMs is less than endMs. Sections

of one song do not overlap.

  • Mark. layer is phrase, word or phoneme. startMs is less than endMs.

A word has a phrase as its parent. A phoneme has a word as its parent. A phrase has no parent. Marks on one layer of one voice do not overlap. A child stays inside the time range of its parent. edited is true after the person changes the mark by hand.

  • Custom entry. word is upper case. symbols is a list of CMU symbols

separated by spaces. Custom entries belong to the browser, not to one song.

  • Run data. One record for each song, in the object store runs (database

version 3). It holds the audio tracks, the singer ranges and the run report of the last completed transcribe run. A new run replaces the full record. Deleting the song deletes it in the same transaction. It holds no lyrics, no label of a mark and no API key. tracks holds vocals and instruments, each { startMs, sampleRate, samples } with 16-bit PCM samples in one channel at 22 050 Hz. A run with no kept tracks, and a record from before issue #129, have no tracks. The storage meter of the song library counts the tracks, because navigator.storage.estimate() counts the full storage of the app.

  • App settings. One record. speechModelId is one of the three supported speech

models. The app does not store device. The app derives the device from the browser on each visit. transcribeSource is browser or remote, and the default is browser. remoteEndpoint holds baseUrl, apiKey and model. The API key stays in this record. No export and no custom dictionary file holds it.

Cross-cutting concerns

  • Auth. None. The app has no accounts and no server data.
  • Privacy. Audio leaves the browser only when the person selects a remote

endpoint, and the app shows the host first. A remote run sends the audio of the song or of the range to that host only. The app sends no lyrics and no marks to any server. The other network requests are for the app files and the speech model files. The API key goes only to the base URL of the remote endpoint.

  • Error handling. Each failure shows a message that states the cause and the

next action. The app never fails without a message. Feature files give the copy.

  • Validation. The app validates at two boundaries only: files that the person

loads, and text that the person types.

  • Persistence. The app saves the open song to IndexedDB 1 second after the last

change. A reload restores the song.

  • Undo. Every change to marks, voices and sections goes through one history

stack with 100 steps.

  • Accessibility. Every control has a keyboard path and a visible focus ring.

Text contrast is 4.5:1 or more. The editor does not rely on colour alone: each phoneme shows its label as text.

  • Themes. The app has a light theme and a dark theme. The default follows the

operating system setting. The browser keeps the choice of the person in localStorage, and the choice wins over the operating system setting.

  • i18n. The UI is English only in v1. Labels accept any Unicode text.
  • Performance targets. The editor scrolls and zooms at 60 frames per second

with 3 000 marks on screen-size hardware from 2020 or later. The first load of the app transfers less than 500 kB compressed, without the dictionary and the speech model.

  • Security posture. The app has no secrets. The app escapes every label that it

writes into XML. The hosting sends a Content-Security-Policy header that allows scripts from the app origin only.

  • Browser support. Current Chrome, Edge and Firefox on desktop. Safari is best

effort. A browser without WebGPU uses the wasm device.

Testing strategy

  • Unit (Vitest). The xtiming writer, the dictionary module, the align

function, the snap function, the store actions and the history stack. These hold the logic, so coverage of these modules is 90% of lines or more.

  • Golden files. The writer tests compare output with .xtiming files in

tests/fixtures/ that match the xLights export format byte for byte.

  • Component (Vitest + Testing Library). Layer rows, drag handles, dialogs.
  • E2E (Playwright). Load the demo song, edit a mark, export, and compare the

download with a golden file. The E2E tests replace the transcribe worker with a fixture, because the speech model is too large for CI.

  • Manual check, once per epic that changes the export. Import the exported file

into xLights and play a Faces effect. The epic records the xLights version.

A change is done when lint, typecheck, unit tests and E2E tests pass, and each acceptance criterion of the issue has a test or a recorded manual check.

Assumptions

  • The app uses hash routes (#/song/<id>), so the hosting needs no rewrite rule.
  • The repository is on GitHub, because the user's tools point there.
  • The licence of the project is MIT. The project writes its own phoneme table from

the facts in the xLights phoneme_mapping file and does not copy that GPL file.

  • The default frame size is 50 ms (20 frames per second). The person can select

25 ms.

  • The app spreads the phonemes of a word evenly across the word. The speech model

gives word times only.

  • The app writes no rest marks by default, because xLights shows rest in gaps.
  • The speech model files come from the Hugging Face Hub at run time. The app does

not copy them to the hosting.

  • The largest audio file is 200 MB and the longest song is 15 minutes.
  • English lyrics only in v1.
  • No analytics and no error reports leave the browser in v1.

Risks & open questions

None of these blocks approval. Each one names the epic that settles it.

  1. Speech model accuracy on songs. Whisper is trained on speech. Music and

harmony lower the accuracy of words and times. Mitigation: the lyrics align flow in features/02-transcription.md and the editor. Epic 2 measured the demo song: the base speech model returned 15 words for the choir clip, with one wrong line. The spec has no accuracy criterion for a song. Vocal separation (to transcribe the voice without the instruments) is an option in the transcribe dialog, off by default (issue #117).

  1. Word times need the right model export. The docs confirm

return_timestamps: 'word'. They do not state which model repositories support it. The onnx-community/whisper-*_timestamped repositories are the candidates. Epic 2 confirms this before any other work.

  1. Download progress. The fetched docs do not describe the progress_callback

option. Epic 2 confirms the option name and the event shape.

  1. Audio input format for the speech model. The docs list Float32Array as an

input type. They do not state the sample rate on the pages read. Epic 2 confirms 16 kHz mono before the resample code is written.

  1. Cross-origin isolation. Multi-thread WASM needs the

Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers. Those headers can block model downloads from another origin. Decided in issue #93: the app sends Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp, and the wasm device uses 2 threads. The base speech model was 1.44 to 1.58 times faster in the measurement. Each cross-origin resource now needs CORS or Cross-Origin-Resource-Policy (ADR 0006).

  1. CMU dictionary format and size. The repository

https://github.com/cmusphinx/cmudict holds cmudict.dict. The entry format and the entry count were not on the page read. Epic 3 confirms both from the file.

  1. Dictionary licence text. The README states unrestricted use with

acknowledgement. Epic 3 copies the LICENSE file into the repository.

  1. AWS account and region. The user names the AWS account and the region of

the S3 bucket in Epic 0. Any command that creates an AWS resource needs the user's confirmation first. The CloudFormation property names for the origin access control and the response headers policy are confirmed on the pages cited. The full template is not verified until Epic 0 deploys it.

  1. Browser storage limits. A browser can evict IndexedDB data under storage

pressure. Epic 1 requests persistent storage and shows the result.
